📚 Comentarios del Código - Explicaciones

Documento que responde a las preguntas e instrucciones encontradas en los comentarios del código.

1. Importación de estilos globales en layout.tsx

Ubicación: app/layout.tsx

Comentario original:

// Hay que importar siempre los estilos que vienen ya predefinidos para que se apliquen al archivo que queramos y empiece a coger forma

Explicación:

En Next.js, los estilos CSS globales deben importarse en el Layout raíz (app/layout.tsx), no en componentes individuales.

❓ ¿Por qué funciona así?

Next.js utiliza un modelo de estilos globales centralizados:

  • Los estilos se importan en el lugar más alto de la jerarquía de componentes
  • El layout.tsx actúa como el contenedor raíz de toda la aplicación
  • Todos los componentes heredan estos estilos

⚠️ Consecuencia:

Si importas CSS global en page.tsx o en otros componentes, causará un error de build porque Next.js no permite importar CSS global desde múltiples lugares (podría haber conflictos).

2. Por qué los estilos globales solo aplican al Layout

Ubicación: app/ui/global.css

Comentario original:

/* Aquí podemos añadir estilos que apliquen a toda la página. Explica por qué solo aplica al layout y por qué si lo importo en el page.tsx no se aplica el estilo */

✅ ¿Por qué aplica en el Layout?

El layout.tsx es el componente raíz que envuelve todo:

export default function RootLayout({ children, }: { children: React.ReactNode; }) { return ( <html lang="en"> <body> {/* Aquí va el children (page.tsx, otros componentes, etc.) */} {children} </body> </html> ); }

Los estilos importados aquí se aplican a todo el HTML que renderiza, incluyendo los children.

✅ ¿Puedo importar CSS global en page.tsx?

Sí, es posible. A diferencia de lo que se creía anteriormente, Next.js permite importar CSS global en componentes como page.tsx, especialmente en versiones recientes.

Esto funciona porque page.tsx sigue siendo parte del árbol de componentes que se renderiza, aunque es recomendable centralizarlo en el Layout para mejor organización.

🎯 Solución: Cómo aplicar estilos específicos a page.tsx

Si quieres estilos específicos para page.tsx, tienes varias opciones:

1. CSS Modules (estilos locales):

import styles from "./page.module.css"; export default function Page() { return <h1 className={styles.title}>Home</h1>; }

2. Tailwind CSS (con clases de utilidad):

export default function Page() { return <h1 className="text-2xl font-bold">Home</h1>; }

3. Estilos inline:

export default function Page() { return <h1 style={{ fontSize: "2rem", fontWeight: "bold" }}>Home</h1>; }

📊 Jerarquía de estilos en Next.js:

app/layout.tsx └── import './ui/global.css' ✅ CSS Global (aplica a todo) └── app/page.tsx └── import './page.module.css' ✅ CSS Local (solo para page) └── className="tailwind-class" ✅ Tailwind (solo para página) └── style={{...}} ✅ Inline (solo para página)

📌 Resumen - Reglas Clave

Regla Descripción
CSS Global en Layout ✅ Se importa en app/layout.tsx
CSS Global en otros archivos ✅ También es posible (aunque mejor centralizarlo en Layout)
CSS Modules ✅ Se usan en componentes específicos (.module.css)
Tailwind/Inline ✅ Se usan directamente en componentes

3. CSS Modules: Estilos Locales para Componentes

Ubicación: app/page.module.css y app/page.tsx

¿Qué son los CSS Modules?

Los CSS Modules son archivos CSS que se importan como objetos JavaScript en componentes React. Cada clase CSS se convierte en una propiedad del objeto, garantizando que los estilos sean locales al componente (no globales).

Ventaja principal: Los nombres de clase se "scopean" automáticamente, evitando conflictos de nombres entre componentes.

📝 Implementación práctica en la home

1. Crear archivo page.module.css:

.homeContainer { display: flex; flex-direction: column; min-height: 100vh; padding: 1.5rem; } .headerBox { display: flex; height: 5rem; align-items: flex-end; border-radius: 0.5rem; background-color: #3b82f6; padding: 1rem; margin-bottom: 1.5rem; } @media (min-width: 768px) { .headerBox { height: 13rem; } } .leftSection { display: flex; flex-direction: column; justify-content: center; gap: 1.5rem; border-radius: 0.5rem; background-color: #f3f4f6; padding: 2.5rem 1.5rem; } .welcomeText { font-size: 1.25rem; color: #1f2937; } .welcomeLink { color: #3b82f6; text-decoration: none; font-weight: 500; } .loginButton { display: flex; align-items: center; gap: 1.25rem; border-radius: 0.5rem; background-color: #3b82f6; padding: 0.75rem 1.5rem; color: white; text-decoration: none; transition: background-color 0.2s ease; } .loginButton:hover { background-color: #60a5fa; }

2. Importar en page.tsx:

import styles from './page.module.css'; export default function Page() { return ( <main className={styles.homeContainer}> <div className={styles.headerBox}> {/* Contenido */} </div> <div className={styles.contentWrapper}> <div className={styles.leftSection}> <p className={styles.welcomeText}> Bienvenido </p> <a className={styles.welcomeLink}>Link</a> <button className={styles.loginButton}> Log in </button> </div> </div> </main> ); }

🔍 ¿Cómo funciona bajo el capó?

Cuando compilas el proyecto, Next.js transforma el CSS Module:

// Lo que defines en page.module.css: .homeContainer { ... } .headerBox { ... } // Se convierte en: // styles.homeContainer = "page_homeContainer__abc123" // styles.headerBox = "page_headerBox__def456" // En el HTML final: <main className="page_homeContainer__abc123"> </main>

Los nombres de clase se hacen únicos globalmente con un hash automático, garantizando que no haya conflictos incluso si otro componente usa .homeContainer.

⚖️ CSS Modules vs Tailwind vs CSS Global

Método Ámbito Caso de uso
CSS Global 🌍 Global (toda la app) Reset, variables, tipografía base
CSS Modules 🏠 Local (componente) Estilos complejos específicos
Tailwind CSS ✨ Clases de utilidad Estilos rápidos y componentes simples
Inline styles 🎯 Específico Estilos dinámicos basados en datos

✅ Ventajas de CSS Modules

  • Sin conflictos de nombres: No importa si otros componentes usan las mismas clases
  • Fácil de mantener: Los estilos viajan con el componente
  • Seguridad de tipos: Si borras una clase, el IDE lo detecta
  • Mejor rendimiento: Solo carga los estilos necesarios para cada página

❌ Consideraciones

  • No puedes usar pseudoelementos globales (necesitan CSS global)
  • Requiere más código que Tailwind para estilos simples
  • Menor reutilización de estilos entre componentes

4. Implementación de Google Fonts: Montserrat

Archivos modificados:

  • app/ui/fonts.ts - Configuración de fuentes
  • app/layout.tsx - Importación y uso

Cómo se implementó:

1. Crear app/ui/fonts.ts:

import { Montserrat } from 'next/font/google'; export const montserrat = Montserrat({ subsets: ['latin'], weight: ['400', '500', '600', '700', '800'], variable: '--font-montserrat', });

2. Importar en app/layout.tsx:

import { montserrat } from './ui/fonts'; export default function RootLayout({ children }) { return ( <html lang="en" className={montserrat.className}> <body>{children}</body> </html> ); }

¿Qué hace cada parte?

  • import { Montserrat } from 'next/font/google' - Trae la fuente desde Google Fonts
  • weight: ['400', '500', '600', '700', '800'] - Especifica qué pesos (grosores) descargar
  • subsets: ['latin'] - Optimiza descargando solo caracteres latinos
  • className={montserrat.className} - Aplica la fuente a todo el HTML

🔍 Autocomplete para localizar fuentes

¿Sabías que hay autocomplete? Cuando importas desde next/font/google, tu editor (VS Code) tiene soporte para autocomplete. Simplemente escribe parte del nombre de la fuente deseada y el IDE te mostrará una lista de opciones disponibles en Google Fonts. Esto hace muy fácil encontrar y seleccionar la fuente perfecta sin necesidad de consultar documentación externa.

Ejemplo de autocomplete:

// Empieza a escribir: import { /* Aquí sale autocomplete */ // Si escribes "Rob" verás: // - Roboto // - Roboto Condensed // - Roboto Flex // - Roboto Mono // - Roboto Serif // etc.
La fuente se descarga automáticamente desde Google Fonts y se sirve optimizada. No necesitas archivos locales ni visitar sitios externos para buscar fuentes.

5. Componente Image de Next.js vs HTML <img>

Ubicación: app/ui/invoices/table.tsx

¿Qué es el componente Image?

Next.js proporciona un componente <Image> optimizado que reemplaza al elemento HTML <img> estándar. Es una evolución que trae múltiples mejoras de rendimiento y funcionalidad.

🖼️ Diferencias principales

1. HTML img normal:

<img src="/customers/avatar.png" alt="Customer avatar" width="32" height="32" />

2. Next.js Image component:

import Image from 'next/image'; <Image src="/customers/avatar.png" alt="Customer avatar" width={32} height={32} />

⚡ Ventajas de usar Image

Característica <img> normal <Image> de Next.js
Optimización automática ❌ No ✅ Sí, convierte a WebP, avif
Carga responsiva ❌ Carga toda la imagen ✅ Carga diferentes tamaños según el dispositivo
Lazy loading automático (carga solo cuando la imagen se ve en pantalla) ❌ Necesita JavaScript ✅ Nativo, no necesita JS
Prevención de Layout Shift ❌ Puede desplazar el contenido ✅ Requiere width/height para evitar cambios
Caché automático ❌ Gestión manual ✅ Integrada en Next.js
Blur placeholder ❌ No disponible ✅ Opción blurDataURL para efecto blur

🎯 Ejemplo práctico con propiedades

import Image from 'next/image'; export default function CustomerAvatar({ imageUrl, name }) { return ( <Image src={imageUrl} alt={`Avatar de ${name}`} width={40} height={40} className="rounded-full" priority={false} placeholder="blur" blurDataURL="data:image/jpeg;base64,..." /> ); }

📋 Propiedades importantes de Image

  • src - Ruta de la imagen (puede ser URL externa)
  • alt - Texto alternativo (obligatorio para accesibilidad)
  • width y height - Dimensiones obligatorias (previenen Layout Shift)
  • priority - Si es true, carga la imagen antes que otras (útil para imágenes "above the fold")
  • placeholder - Puede ser "blur" o "empty" para mostrar algo mientras carga
  • quality - Calidad de la imagen (1-100), por defecto 75
  • fill - Alterna a true si quieres que ocupe un contenedor padre

⚠️ Cuándo usar cada uno

Usa <Image> de Next.js cuando:
  • Necesitas optimización automática
  • La imagen aparece en múltiples páginas
  • Quieres mejorar el Core Web Vitals (LCP, CLS)
  • Trabajas con imágenes en formatos antiguos (JPG, PNG)
Puedes usar <img> cuando:
  • Necesitas un SVG (no necesita optimización)
  • Es una imagen dinámica generada en tiempo real
  • Requieres máxima flexibilidad sin restricciones de Next.js
Recomendación: Prefiere siempre <Image> en Next.js. Es mejor para el rendimiento y está optimizado automáticamente. Solo usa <img> cuando tengas una razón específica.

6. Enrutado Basado en el Sistema de Archivos (File-based Routing)

¿Qué es el file-based routing?

Next.js utiliza un sistema de enrutado automático basado en la estructura de carpetas y archivos dentro de la carpeta app. No necesitas configurar rutas manualmente como en otros frameworks (Express, etc.). La carpeta define la ruta URL.

Regla de oro: Cada carpeta en app se convierte en un segmento de la ruta URL, y los archivos page.tsx son los que renderizan la página.

📁 Estructura de carpetas = Rutas URL

app/ ├── page.tsx ➜ GET / ├── about/ │ └── page.tsx ➜ GET /about ├── products/ │ └── page.tsx ➜ GET /products │ └── [id]/ │ └── page.tsx ➜ GET /products/:id (dinámico) └── dashboard/ ├── layout.tsx ➜ Layout específico para /dashboard y sus hijos ├── page.tsx ➜ GET /dashboard ├── invoices/ │ ├── page.tsx ➜ GET /dashboard/invoices │ └── [id]/ │ └── page.tsx ➜ GET /dashboard/invoices/:id └── customers/ └── page.tsx ➜ GET /dashboard/customers

🎯 Ejemplo práctico: Ruta /dashboard

1. Crear la estructura de carpetas:

app/ └── dashboard/ ├── layout.tsx (opcional: layout específico del dashboard) └── page.tsx (la página que se renderiza en /dashboard)

2. Contenido de app/dashboard/page.tsx:

import { Card } from '@/app/ui/dashboard/cards'; import { LatestInvoices } from '@/app/ui/dashboard/latest-invoices'; export default function DashboardPage() { return ( <main> <h1>Dashboard</h1> <div className="grid grid-cols-4 gap-4"> <Card title="Total Revenue" value="$45,231" /> <Card title="Pending Invoices" value="12" /> <Card title="Total Customers" value="348" /> </div> <LatestInvoices /> </main> ); }

3. Acceder a la página:

// URL en el navegador: http://localhost:3000/dashboard // Desde el código (con Link de Next.js): import Link from 'next/link'; export default function Nav() { return ( <nav> <Link href="/dashboard"> Dashboard </Link> </nav> ); }

📂 Convenciones especiales en Next.js

Archivo Propósito Ejemplo
page.tsx La página principal de la ruta app/dashboard/page.tsx ➜ /dashboard
layout.tsx Layout compartido para esa ruta y sus hijas app/dashboard/layout.tsx envuelve /dashboard y subcarpetas
[id] Segmento dinámico (parámetro de ruta) app/products/[id]/page.tsx ➜ /products/123
[...slug] Segmento dinámico que captura múltiples niveles app/docs/[...slug]/page.tsx ➜ /docs/guides/intro
route.ts Endpoint de API REST app/api/users/route.ts ➜ POST /api/users

🏗️ Estructura típica de un proyecto

app/ ├── layout.tsx (Layout raíz - envuelve toda la app) ├── page.tsx (Página home: /) ├── dashboard/ │ ├── layout.tsx (Layout del dashboard) │ ├── page.tsx (/dashboard) │ ├── invoices/ │ │ ├── page.tsx (/dashboard/invoices) │ │ ├── [id]/ │ │ │ └── page.tsx (/dashboard/invoices/123) │ │ └── create/ │ │ └── page.tsx (/dashboard/invoices/create) │ └── customers/ │ ├── page.tsx (/dashboard/customers) │ └── [id]/ │ └── page.tsx (/dashboard/customers/456) ├── login/ │ └── page.tsx (/login) ├── api/ │ ├── users/ │ │ └── route.ts (GET/POST /api/users) │ └── invoices/ │ └── [id]/ │ └── route.ts (GET/PUT /api/invoices/123) └── ui/ └── (componentes compartidos, no generan rutas)

✨ Ventajas del file-based routing

  • Intuitivo: La estructura de carpetas refleja directamente las rutas
  • Escalable: Fácil agregar nuevas páginas solo creando carpetas
  • Sin configuración: No necesitas archivos de configuración de rutas
  • Colocación de archivos: Puedes poner CSS modules, componentes cerca de la página
  • Layouts anidados: Cada carpeta puede tener su propio layout

6.1 - Subrutas: Truco para crearlas rápidamente

Una subruta es una ruta anidada dentro de otra. Por ejemplo, /dashboard/customers es una subruta de /dashboard. Aquí viene un truco muy útil:

¿Sabías este truco de VS Code? En VS Code, puedes crear un archivo con una ruta que no existe aún. El editor creará automáticamente todas las carpetas intermedias. Por ejemplo, si haces clic derecho en la carpeta app/dashboard y eliges "New File", puedes escribir:

customers/page.tsx

VS Code creará automáticamente la carpeta customers y dentro el archivo page.tsx, ¡sin necesidad de crearlas manualmente!

Ejemplo: Crear /dashboard/customers

app/ └── dashboard/ ├── page.tsx (/dashboard) └── customers/ └── page.tsx (/dashboard/customers) ← NUEVA SUBRUTA

Cómo usar el truco:

  1. Haz clic derecho en la carpeta donde quieres crear el archivo (ej: app/dashboard)
  2. Selecciona "New File"
  3. Escribe la ruta completa: customers/page.tsx
  4. Presiona Enter
  5. VS Code crea automáticamente la carpeta y el archivo
Funciona también para rutas más profundas:
customers/[id]/edit/page.tsx
VS Code crea todas las carpetas intermedias automáticamente.
Pro tip: Usa la carpeta (grupo) con paréntesis para organizar rutas sin afectar la URL. Ejemplo: app/(auth)/login/page.tsx sigue siendo /login pero está organizado bajo "auth".

🎨 Layouts en Rutas Anidadas

Concepto:

En Next.js, cada carpeta de ruta puede tener su propio archivo layout.tsx. Este layout se aplicará a todos los componentes dentro de esa carpeta y sus subcarpetas.

Estructura de ejemplo:

app/ ├── layout.tsx (Layout raíz - se aplica a toda la app) ├── page.tsx (Página principal) └── dashboard/ ├── layout.tsx (Layout del dashboard - se aplica solo a rutas dentro de /dashboard) ├── page.tsx (Página del dashboard) ├── invoices/ │ ├── page.tsx (Usa el layout de /dashboard) │ └── [id]/ │ └── page.tsx (Usa el layout de /dashboard) └── customers/ └── page.tsx (Usa el layout de /dashboard)

✅ ¿Cómo funciona?

El layout de una ruta se aplica a todas las subrutas dentro de esa carpeta:

  • El layout.tsx envuelve el contenido de page.tsx
  • Los layouts se anidan según la estructura de carpetas
  • Cada layout puede tener su propio diseño, estilos y componentes
  • La URL no se ve afectada por los layouts

Ejemplo práctico - Dashboard con sidebar:

// app/dashboard/layout.tsx import SideNav from '@/app/ui/dashboard/sidenav'; export default function DashboardLayout({ children, }: { children: React.ReactNode; }) { return ( <div className="flex h-screen"> <div className="w-64"> <SideNav /> </div> <div className="flex-grow"> {/* Aquí van todas las páginas dentro de /dashboard */} {children} </div> </div> ); }

📊 Jerarquía de layouts:

Cuando accedes a /dashboard/invoices:

  1. Se renderiza el layout.tsx raíz (de app/)
  2. Dentro de él, se renderiza el layout.tsx del dashboard (de app/dashboard/)
  3. Dentro de ese, se renderiza el page.tsx de invoices

💡 Casos de uso:

  • Dashboard: Sidebar + contenido principal
  • Blog: Barra lateral con categorías + artículos
  • Autenticación: Layout especial solo para rutas protegidas
  • Admin Panel: Layout diferente al sitio público
Pro tip: Los layouts son muy útiles para mantener UI consistente en un grupo de rutas, como un sidebar que debe aparecer en todas las páginas del dashboard, pero no en otras secciones.

7. Navegación por la Web

⚠️ El problema actual:

Hasta ahora, cada vez que navegamos a una nueva página (por ejemplo, haciendo clic en un enlace), la página completa se recarga. Esto sucede porque estamos usando etiquetas HTML tradicionales <a> que causan una recarga completa del servidor.

¿Qué pasa cuando navegas con un <a> tradicional?

<a href="/dashboard/invoices">Ver Facturas</a> // El navegador: // 1. Envía una solicitud HTTP al servidor // 2. El servidor renderiza la página completa // 3. El navegador descarga todo (HTML, CSS, JavaScript) // 4. La página se recarga completamente ⟷️ Parpadeo, pérdida de scroll, etc.

💡 La solución en Next.js: Componente Link

Next.js proporciona el componente <Link> que implementa navegación del lado del cliente (Client-side Navigation):

import Link from 'next/link'; export default function NavLinks() { return ( <nav> <Link href="/dashboard/invoices"> Ver Facturas </Link> </nav> ); }

✅ Beneficios de usar <Link>:

  • Sin recarga completa: Solo se actualiza el contenido que cambió
  • Más rápido: No descarga CSS/JavaScript innecesarios
  • Mejor UX: La página no parpadea, se conserva el scroll, animaciones suaves
  • Pre-fetching: Next.js precarga las páginas automáticamente
  • Preserva estado: Los componentes mantienen su estado durante la navegación
Regla importante: Siempre usa <Link> de Next.js en lugar de <a> para enlaces internos. Solo usa <a> para enlaces externos.

Comparativa:

Aspecto <a> tradicional <Link> de Next.js
Recarga de página ✅ Sí, completa ❌ No, solo contenido
Velocidad ❌ Lenta ✅ Rápida
Parpadeo ✅ Sí ❌ No
Preserva estado ❌ Se pierde ✅ Se mantiene
Pre-fetching ❌ No ✅ Automático

🔧 Implementación en nuestro proyecto:

Se ha actualizado el componente NavLinks (app/ui/dashboard/nav-links.tsx) para usar <Link> de Next.js en lugar de etiquetas <a> tradicionales.

Cambio realizado:

// ❌ Antes (etiquetas <a> - recargaban la página completa) <a href={link.href}> {link.name} </a> // ✅ Ahora (componente Link de Next.js - navegación del lado del cliente) import Link from 'next/link'; <Link href={link.href}> {link.name} </Link>

Resultado: Cuando ahora haces clic en los enlaces del navegador (Home, Invoices, Customers), la página NO se recarga completamente. Solo el contenido relevante se actualiza, ofreciendo una experiencia más rápida y fluida.

Nota: El componente <Link> de Next.js es diferente al componente <Link> de React Router. Asegúrate de importarlo de 'next/link'.

🎣 8. Hooks

usePathname

usePathname es un Hook de Next.js que devuelve la ruta actual (pathname) de la página en la que te encuentras.

❓ ¿Qué es el pathname?

El pathname es la parte de la URL que viene después del dominio. Por ejemplo:

https://ejemplo.com/dashboard/invoices ↑ pathname /dashboard/invoices

💡 Casos de uso:

  • Destacar el enlace activo en el navegador
  • Mostrar/ocultar componentes según la ruta actual
  • Aplicar estilos diferentes según dónde estés

📦 ¿De dónde se importa?

Se importa desde 'next/navigation':

import { usePathname } from 'next/navigation';

📝 Ejemplo práctico:

import { usePathname } from 'next/navigation'; export default function NavLinks() { const pathname = usePathname(); return ( <nav> <a href="/dashboard" className={pathname === '/dashboard' ? 'active' : ''} > Home </a> <a href="/dashboard/invoices" className={pathname === '/dashboard/invoices' ? 'active' : ''} > Invoices </a> </nav> ); }

Lo que ocurre: El link que coincida con la ruta actual recibirá la clase active para destacarse visualmente.

⚠️ Error: "This React Hook only works in a Client Component"

Cuando usas usePathname en un componente, probablemente recibirás este error:

Error: You're importing a component that needs usePathname. This React Hook only works in a Client Component. To fix, mark the file (or its parent) with the "use client" directive.

❓ ¿Por qué sucede?

En Next.js 13+, por defecto todos los componentes son Server Components (se ejecutan en el servidor). Los Hooks como usePathname necesitan acceso al navegador del cliente para funcionar, por lo que solo pueden usarse en Client Components (se ejecutan en el navegador).

🖥️ ¿Qué significa "ejecutarse en el servidor"?

Cuando un componente se ejecuta en el servidor, significa que:

  • El código corre en el servidor: Toda la lógica del componente se ejecuta en el servidor web (en donde está alojada tu app), NO en el navegador del usuario
  • Se convierte a HTML: El componente React se procesa/renderiza y se convierte en HTML puro
  • Se envía al navegador: El HTML resultante se envía al navegador del usuario
  • No interactúa con el cliente: El componente no tiene acceso a información del navegador (como la URL actual, clicks, etc.)

Flujo de un Server Component:

Usuario hace request ↓ Servidor ejecuta el componente React ↓ Servidor genera HTML ↓ HTML se envía al navegador ↓ Usuario ve la página renderizada

Flujo de un Client Component:

Usuario hace request ↓ Servidor envía HTML + JavaScript ↓ Navegador descarga el JavaScript ↓ JavaScript se ejecuta EN EL NAVEGADOR ↓ El componente se renderiza en el navegador ↓ Usuario interactúa con el componente (clicks, hover, etc.) ↓ JavaScript responde a las interacciones
Importante: Los Hooks como usePathname() necesitan información del navegador (la URL actual, por ejemplo). Un Server Component no tiene acceso a esa información porque se ejecuta en el servidor, no en el navegador. Por eso necesitas marcar el componente como Client Component con 'use client'.

✅ La solución: "use client"

Debes marcar el archivo con la directiva "use client" al inicio del archivo. Esto le indica a Next.js que este componente debe renderizarse en el cliente:

'use client'; import Link from 'next/link'; import { usePathname } from 'next/navigation'; import { UserGroupIcon, HomeIcon } from '@heroicons/react/24/outline'; export default function NavLinks() { const pathname = usePathname(); // ... resto del código }

📌 Server Components vs Client Components:

Característica Server Component Client Component
Renderiza en Servidor Navegador del cliente
Hooks (useState, useEffect, usePathname) ❌ No permitidos ✅ Permitidos
Acceso a datos privados ✅ Seguro ❌ Expuesto al cliente
Tamaño del bundle ✅ Más pequeño ❌ Más grande

📦 9. Code Splitting

¿Qué es Code Splitting?

Code Splitting es una técnica en la que el código de tu aplicación se divide en múltiples archivos más pequeños (chunks), en lugar de enviar todo el código en un único archivo grande. Cada chunk se carga solo cuando es necesario.

🎯 ¿Por qué es importante?

Si toda tu aplicación estuviera en un único archivo JavaScript gigante:

  • Descarga lenta: El navegador tendría que descargar TODO el código, incluso las partes que no necesita
  • Peor rendimiento: Cuanto más código, más tiempo para procesar y renderizar
  • Mayor consumo de datos: Los usuarios descargan código innecesario

✅ Beneficios del Code Splitting:

  • Descarga inicial más pequeña: Solo se descarga el código necesario para la página actual
  • Carga más rápida: Menos código = carga más rápida
  • Mejor rendimiento: El navegador puede procesar el código más rápido
  • Menor uso de datos: Los usuarios solo descargan lo que necesitan

🔧 Cómo Next.js lo hace automáticamente:

Next.js ya hace Code Splitting automáticamente:

  1. Por ruta: Cada página (ej: /dashboard, /dashboard/invoices) es un chunk separado
  2. Por componente: Los componentes se pueden dividir en chunks más pequeños
  3. Lazy Loading: Los componentes se cargan solo cuando se necesitan

Ejemplo práctico:

// Sin Code Splitting (todo en un archivo): // bundle.js (500KB) - Código de /dashboard - Código de /dashboard/invoices - Código de /dashboard/customers - Componentes del dashboard - Utilidades - Librerías externas // Con Code Splitting (varios archivos): // main.js (50KB) - código común de todas las páginas // dashboard.js (80KB) - código específico de /dashboard // invoices.js (90KB) - código específico de /dashboard/invoices // customers.js (85KB) - código específico de /dashboard/customers

📊 Cómo funciona la carga:

Usuario accede a /dashboard ↓ Se descarga main.js + dashboard.js ↓ Usuario navega a /dashboard/invoices ↓ Se descarga invoices.js (rest ya estaba cargado) ↓ Usuario navega a /dashboard/customers ↓ Se descarga customers.js
Ventaja de Next.js: La navegación entre rutas usa Client-side Navigation (que vimos antes), por lo que los chunks se cargan de forma inteligente sin recargar la página completa.

💡 En nuestro proyecto:

Cuando usamos <Link> para navegar entre /dashboard, /dashboard/invoices y /dashboard/customers, Next.js automáticamente:

  1. Descarga solo el código necesario para esa página
  2. Precarga el código de las páginas relacionadas (al hacer hover en un link)
  3. Renderiza la página sin recargar completamente

🗄️ 10. Crear Base de Datos en Vercel

❓ ¿Por qué necesitamos una base de datos?

Una base de datos permite almacenar, organizar y recuperar datos de manera persistente. En nuestro caso, necesitamos almacenar información sobre facturas (invoices) y clientes. A diferencia de los datos ficticios que hemos usado hasta ahora, una base de datos real permite guardar información que persiste entre sesiones.

🔗 ¿Qué es Vercel Storage?

Vercel Storage es el servicio de almacenamiento en la nube de Vercel que permite usar bases de datos directamente integradas con tu aplicación. Ofrece varias opciones:

  • Postgres Serverless: Base de datos SQL relacional
  • Redis: Base de datos en memoria para caching
  • Blob Storage: Almacenamiento de archivos

📚 ¿Qué es Neon?

Neon es un proveedor de Postgres Serverless. Ofrece una base de datos PostgreSQL completamente administrada sin necesidad de mantenimiento del servidor. Es ideal para aplicaciones de Next.js porque:

  • Escalable: Se ajusta automáticamente según la carga
  • Seguro: Gestiona automáticamente copias de seguridad y actualizaciones
  • Rápido: Infraestructura optimizada con baja latencia
  • Gratuito hasta cierto límite: Perfecto para proyectos pequeños y aprendizaje

🚀 Pasos para crear la base de datos:

1. Acceder a Vercel Storage

Ir a tu proyecto en Vercel ↓ Dashboard → Tu Proyecto ↓ Menú lateral → Pestaña "Storage" ↓ Botón "+ Create Database" / "Nueva Base de Datos"

2. Seleccionar Postgres Serverless

Vercel te mostrará varias opciones de bases de datos. Debes seleccionar "Postgres Serverless" que es el tipo de base de datos relacional.

¿Por qué Postgres? PostgreSQL es una base de datos relacional muy poderosa y es el estándar en la industria. Es perfecto para aplicaciones que necesitan tablas relac ionadas con datos normalizados.

3. Seleccionar el proveedor: Neon

Una vez seleccionado Postgres, Vercel te pedirá que elijas un proveedor. Las opciones típicas son:

  • Neon (recomendado) - Muy popular, buena relación precio/rendimiento
  • PlanetScale - Otra alternativa
  • Otros proveedores según disponibilidad

Selecciona Neon como proveedor.

4. Elegir la región: Frankfurt

Neon te pedirá que selecciones una región geográfica donde se alojará la base de datos. Las regiones disponibles suelen incluir:

Estados Unidos (us-east-1, us-west-1) Europa (eu-west-1, eu-central-1) Asía (ap-southeast-1, ap-northeast-1) etc.
Importante: Debes seleccionar Frankfurt (eu-central-1) porque es la región más cercana a tu ubicación. Una región cercana reduce la latencia (tiempo de respuesta) entre tu aplicación y la base de datos.

💡 ¿Qué es la latencia?

La latencia es el tiempo que tarda una solicitud desde tu aplicación hasta la base de datos y la respuesta de vuelta. Si el servidor está lejos geográficamente, la latencia será mayor, haciendo que las consultas sean más lentas. Frankfurt es la región más cercana a Europa, por lo que garantiza la menor latencia para usuarios europeos.

5. Nombrar la base de datos

En el último paso, Neon/Vercel te pedirá un nombre para tu base de datos. Este es un nombre descriptivo (no afecta a la funcionalidad).

Nombre sugerido: create-invoices (También podrían ser: my-invoices, invoicing-app, dashboard-db, etc.)

En este caso, hemos elegido create-invoices porque refleja que es una aplicación para crear y gestionar facturas.

6. Confirmar y crear

Una vez completados los pasos anteriores, haz clic en el botón de confirmación (a menudo llamado "Create", "Crear", "Connect", etc.). Vercel procedará a:

  1. Comunicarse con Neon
  2. Crear una nueva instancia de Postgres en la región Frankfurt
  3. Configurar las credenciales de conexión automáticamente
  4. Mostrar las variables de entorno necesarias

📋 Lo que obtendrás después de crear la BD:

Una vez creada, Vercel te mostrará información importante:

  • Connection String: La cadena de conexión (contiene todas las credenciales)
  • Host: Servidor de la BD
  • Database: Nombre de la BD
  • User: Usuario para conectarse
  • Password: Contraseña
  • Variables de entorno: .env.local automáticamente configurado
Vercel hace todo automáticamente: Las variables de entorno se agregan automáticamente a tu proyecto. NO tienes que copiar/pegar manualmente las credenciales, Vercel se encarga de todo.

🔐 Seguridad:

  • Connection String: Nunca la compartas públicamente
  • Variables de entorno: Se guardan en .env.local (NO se versionan en Git)
  • Password: Neon genera una contraseña fuerte automáticamente
  • Conexiones SSL: Las conexiones a la BD van cifradas

Una vez creada la base de datos, necesitarás:

  1. Instalar un cliente de Postgres: Para conectarte desde tu aplicación (como pg o prisma)
  2. Crear tablas: Definir la estructura (facturas, clientes, etc.)

🔑 10.1 Copiar Variables de Entorno desde Vercel

¿Qué son las variables de entorno?

Las variables de entorno son configuraciones sensibles (como contraseñas, URLs de servidor, claves API) que se almacenan fuera del código. No deben estar en el repositorio Git por razones de seguridad.

📁 .env vs .env.local - ¿Cuál es la diferencia?

Next.js utiliza un sistema de archivos de configuración con prioridad. Es muy importante entender la diferencia:

Archivo .env .env.local
Propósito Variables por defecto/ejemplo Variables locales (reales/secretas)

Nota importante: Ambos archivos (.env y .env.local) están listados en .gitignore, así que ninguno se versiona en Git por seguridad. Pega las variables de Vercel en el archivo que uses (.env o .env.local), da igual.

🌱 10.2 Ejecutar el Script Seed para Llenar la BD

¿Qué es un seed?

Un seed es un script que llena tu base de datos con datos iniciales de prueba. Es útil para tener datos listos mientras desarrollas tu aplicación sin tener que crear todo manualmente.

🏗️ Cómo funciona el seed en este proyecto

El seed está implementado como un endpoint HTTP (ruta de Next.js), no como un script CLI. Esto significa que se ejecuta visitando una URL en tu navegador, no mediante un comando en terminal.

Diferencia importante: En algunos cursos antiguos, el seed era un archivo ejecutable independiente (.scripts/seed.js). En este proyecto (Next.js moderno), el seed es una API route ubicada en app/seed/route.ts con un manejador HTTP GET().

📂 Ubicación del seed

El archivo que contiene el seed está en:

📁 Tu proyecto ├── app/ │ ├── seed/ │ │ └── route.ts ← Aquí está el seed │ ├── layout.tsx │ └── page.tsx └── ...

🔍 Estructura del archivo route.ts (con explicación)

Sección Propósito
Importaciones Trae el cliente de Postgres para conectar a la BD

📋 ¿Por qué no hay comando "npm run seed"?

Algunos desarrolladores esperan un comando npm run seed en la terminal (como los bancos de datos tradicionales). Sin embargo, este proyecto NO tiene ese comando, y es intencional.

Razón: El seed está implementado como un endpoint HTTP (ruta de Next.js), no como un script ejecutable independiente.

¿Por qué? Porque:
  • El archivo app/seed/route.ts es una ruta de Next.js que necesita el servidor corriendo
  • Las funciones de seed importan desde placeholder-data.ts, que es parte del proyecto Next.js
  • No se puede ejecutar como un script CLI tradicional (aunque lo teníamos configurado, no funcionaba correctamente)

La forma correcta es siempre: Visitar http://localhost:3000/seed en el navegador (con el servidor corriendo).

Si alguna vez necesites un seed CLI tradicional, tendrías que crear un archivo separado en .scripts/seed.ts con acceso directo a la BD, pero la forma actual (por HTTP) es la recomendada en Next.js moderno porque garantiza que todo funcione correctamente.
